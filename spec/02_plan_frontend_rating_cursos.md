# Plan de Implementación — Frontend: Sistema de Rating de Cursos

Plan elaborado por el subagente de frontend a partir del análisis técnico en [00_rating_cursos.md](./00_rating_cursos.md), verificado contra el código real de `Frontend/` (`src/types/index.ts`, `src/components/Course/`, `src/components/CourseDetail/`, `src/app/`, `.cursor/rules/`, `vitest.config.ts`, `package.json`).

**Precondición (fuera de este plan, solo dependencia):** Backend con `rating_average`/`rating_count` en `GET /courses` y `GET /courses/:slug`, y `POST /courses/:slug/ratings` implementado y con sus tests en verde (ver [01_plan_backend_rating_cursos.md](./01_plan_backend_rating_cursos.md)). No arrancar Fase 1 antes de eso.

## Verificación contra el código real

Los supuestos base del architect son correctos (`CourseDetail extends Course`, convención de 3 archivos co-ubicados, `styles/vars.scss` con función `color()`), pero se encontraron varios puntos que el architect no consideró o dejó implícitos:

- **No existe cliente HTTP centralizado, y las 3 llamadas GET existentes no viven en componentes.** `src/app/page.tsx`, `src/app/course/[slug]/page.tsx` y `src/app/classes/[class_id]/page.tsx` son Server Components que hacen `fetch("http://localhost:8000/...", { cache: "no-store" })` inline, con la URL hardcodeada (sin variable de entorno). El `RatingForm` será el primer `fetch` que corre **en el navegador** (Client Component), no en el servidor — mismo host funciona en dev, pero es un patrón nuevo, no una reutilización de uno existente.
- **Confirmado: cero `"use client"` reales hoy.** El único match de `"use client"` en todo `src/` es el error boundary de Next (`course/[slug]/error.tsx`), que es boilerplate obligatorio de Next, no interactividad de UI. `RatingForm` es efectivamente el primer client component interactivo del Frontend, tal como asume el architect.
- **`Course.tsx` (card de listado) excluye `slug` explícitamente:** `type CourseProps = Omit<CourseType, "slug">`, y `src/app/page.tsx` le pasa props sueltas, no el objeto `course` completo. Esto es más restrictivo de lo que el architect dejó ver: agregar el `StarRating` de solo lectura ahí solo requiere sumar `rating_average`/`rating_count` a la desestructuración; **no** se toca `slug` porque el listado no necesita el `RatingForm` interactivo (eso vive en el detalle, que sí tiene el objeto completo).
- **`CourseDetailComponent` es Server Component sin estado**, renderizado desde un `page.tsx` que también es Server Component con `cache: "no-store"`. El architect no abordó cómo se refleja el nuevo promedio después de votar: al insertar `RatingForm` (client) como hijo esto funciona sin problema en App Router, pero hace falta decidir explícitamente la estrategia de refresco (candidato natural: `router.refresh()` tras el POST exitoso, ya que el padre ya depende de datos frescos sin caché).
- **No hay `CourseDetail.test.tsx`** — no hay test que "actualizar" ahí como sí lo hay en `Course.test.tsx`.
- **Sin librería de iconos ni `@testing-library/user-event` en `package.json`** (coherente con el minimalismo del proyecto: sin axios, sin Tailwind, sin state libs). Implica: estrellas como caracteres/SVG inline (no agregar dependencia de iconos), y tests de interacción con `fireEvent` de `@testing-library/react` (ya disponible) salvo decisión explícita de sumar `user-event`.
- **`styles/vars.scss` no tiene ningún tono dorado/amarillo** en el mapa `$colors` (solo `primary` rojo, neutros y textos) — hace falta agregar una entrada nueva antes de poder usar `color('...')` en el SCSS de las estrellas, si se quiere respetar la convención documentada.
- Confirmado (sin cambios): la carpeta `__test__/` de `Course.test.tsx` es inconsistente con la convención plana documentada; los componentes nuevos deben seguir la convención correcta, no replicar la inconsistencia.

## Plan de implementación (por fases)

- Agregar tipo para el body del POST (`{ stars: number }`) y tipo para la respuesta del agregado (`{ rating_average: number | null, rating_count: number }`), reutilizable entre `RatingForm` y cualquier lectura futura.
- **Checkpoint:** `npm run lint` / compilación TypeScript sin errores; ningún componente existente se rompe todavía porque nada consume aún los campos nuevos.
- **Resultado:** agregados `Course.rating_average`/`Course.rating_count`, y los tipos `RatingCreate`/`RatingSummary`. `npm run lint` sin errores nuevos. `tsc --noEmit` marcó (esperadamente) `page.tsx` y `Course.test.tsx` como incompletos hasta la Fase 4 — resuelto al cerrar esa fase.

- SCSS: agregar primero el token de color faltante (dorado/estrella) en `src/styles/vars.scss`, dentro del mapa `$colors` existente, y consumirlo vía `color('...')` en `StarRating.module.scss`.

### Fase 3 — Componente `RatingForm` (interactivo, `"use client"`) ✅ Completada
- Crear `src/components/RatingForm/RatingForm.tsx`, `RatingForm.module.scss`, `RatingForm.test.tsx`.
- Marcar `"use client"` (primer uso real de esta directiva para interactividad en el proyecto). Recibe `slug` como prop; maneja estado local (estrella seleccionada, loading, error, éxito) con `useState`.
- El `fetch` del POST corre en el navegador: seguir el mismo estilo que las llamadas GET existentes (URL hardcodeada `http://localhost:8000/courses/${slug}/ratings`, sin introducir una capa de cliente HTTP no solicitada) pero dejar explícito en el propio código/comentario que es el primer fetch client-side del proyecto, por si luego se decide centralizar.
- Manejar estados: idle → enviando → éxito (mostrar el `rating_average`/`rating_count` devueltos por el POST) → error (404 curso no encontrado / 422 valor inválido / error de red).
- Test: mockear `global.fetch` con `vi.fn()`/`vi.stubGlobal` (no hay MSW instalado); simular clicks con `fireEvent` (no hay `user-event` instalado); cubrir éxito, error de red y respuesta no-ok.
- **Checkpoint:** `npm run test` en verde para `RatingForm.test.tsx` de forma aislada; `npm run lint` sin warnings de reglas de hooks/cliente.
- **Resultado:** componente creado con estados idle/submitting/success/error. 4 tests en verde (éxito con nuevo promedio, 404, 422, error de red). `npm run lint` sin warnings nuevos.

### Fase 5 — Integración en el detalle (`CourseDetailComponent`) y estrategia de sincronización ✅ Completada
- En `src/components/CourseDetail/CourseDetail.tsx` (Server Component, recibe `course` completo con `slug`): renderizar `StarRating` (solo lectura, con los datos ya traídos server-side) y `RatingForm` (client component hijo, pasándole `course.slug`).
- Decisión de diseño que el architect no cubrió: cómo se refleja el nuevo promedio tras votar, dado que el padre es Server Component sin estado. Recomendado: que `RatingForm`, al recibir una respuesta 201 exitosa, llame a `router.refresh()` (`next/navigation`) para que Next vuelva a ejecutar el `page.tsx` de `/course/[slug]` (ya usa `cache: "no-store"`, consistente con este approach) y el `StarRating` server-rendered quede actualizado. Alternativa más simple (documentar cuál se eligió): que `RatingForm` solo muestre su propio resultado post-voto sin tocar el `StarRating` de al lado hasta el próximo refresh manual.
- **Checkpoint:** prueba manual con backend real corriendo — votar y confirmar que el promedio/contador visibles se actualizan según la estrategia elegida.
- **Resultado:** se eligió `router.refresh()` (estrategia recomendada). `RatingForm.test.tsx` mockea `next/navigation` y confirma que `refresh()` se llama tras un 201 exitoso y no se llama en la rama de error (5 tests en verde). ## Errores encontrados durante la implementación y cómo se corrigieron

1. **Colisión de accesibilidad `role="img"` (Fase 4):** el diseño inicial de `StarRating` envolvía el componente en un `<div role="img" aria-label="...">`, duplicando el rol implícito `img` del `<img>` del thumbnail y rompiendo `Course.test.tsx` (`getByRole("img")` con match múltiple). Corregido quitando ese `role`/`aria-label` del wrapper; el texto visible ("4.5 (12 votos)" / "Sin votos aún") ya es suficiente como contenido accesible.
2. **Warning de `act()` en `CourseDetail.test.tsx` (Fase 6):** el test que simula un voto disparaba una actualización de estado asíncrona (la promesa del `fetch` mockeado) sin esperarla, generando el warning "An update to RatingForm inside a test was not wrapped in act(...)". Corregido agregando un `await waitFor(...)` tras el `fireEvent.click` para esperar la actualización antes de terminar el test.
3. **`npm run build` fallaba por un error de tipos preexistente y ajeno al rating (Fase 7):** Next.js 15 exige que `params` en las páginas de rutas dinámicas (`app/**/page.tsx`) sea un `Promise<{...}>`, no un objeto plano — `src/app/course/[slug]/page.tsx` y `src/app/classes/[class_id]/page.tsx` seguían la convención antigua (`params: { slug: string }`), un desajuste que ya existía antes de esta sesión (confirmado con `git log`, ninguno de los dos archivos fue tocado en fases anteriores) y que bloqueaba el build de **cualquier** cambio, no solo del rating. Se corrigió tipando `params` como `Promise<{...}>` y haciendo `await params` en ambas páginas (`CoursePage`/`generateMetadata` y `ClassPage`), y se ajustó `classes/[class_id]/page.test.tsx` para pasar `Promise.resolve({ class_id: "19" })` en vez de un objeto plano, consistente con el nuevo tipo.
4. **Dos errores de lint preexistentes bloqueaban `npm run build` (Fase 7):** `next build` trata los errores de ESLint (no solo warnings) como fallos de build. `'id' is defined but never used'` en `Course.tsx` (la prop `id` ya estaba destructurada sin usarse antes de esta sesión) y `'startTransition' is defined but never used'` en `classes/[class_id]/page.test.tsx` (import sin uso, también preexistente). Corregidos quitando `id` de la desestructuración de `Course.tsx` (sigue existiendo en el tipo `CourseProps`, solo no se desestructura) y el import no usado de `startTransition`.
5. **No corregido, fuera de alcance:** `classes/[class_id]/page.test.tsx` sigue fallando en `npm run test` con "A component suspended while responding to synchronous input" — es un problema preexistente de cómo el test usa `renderToString` sobre un Server Component `async` con `fetch`, ajeno al rating; solo se corrigió su error de tipos (punto 3) para que compilara, no el problema de renderizado en sí.
6. **Efecto colateral de `npm install` (sesión anterior, Fases 1-4):** al no existir `node_modules` instalados, `npm install` reescribió `Frontend/yarn.lock` (el proyecto usa `yarn`) y generó un `package-lock.json`. Se revirtió `yarn.lock` con `git checkout` y se borró el `package-lock.json` generado, dejando el diff limpio.
